Bringing village history out of the archive

Answers from the museum's own sources, every statement backed by issue and page.

Old chronicles, annual publications and photo collections are full of stories about a village, yet they mostly sit in boxes and PDF files. For a village museum I am building a chat assistant that makes this knowledge searchable. Anyone asking about an old farmstead, a street or a trade gets an answer from the original sources and sees the matching pictures.

The project

I am building a prototype with a clear goal: the valuable publications and photos of the Birmensdorf village museum should become accessible to the public, especially to the people living in the village. After extensive testing with users, the chat is to go live. The method is called Retrieval-Augmented Generation (RAG): the language model does not answer from its own knowledge, but from passages that were first retrieved from the collection.

The starting point

Over decades, a local history association has published writings on the village's history and built up an extensive photo archive. The knowledge sits in PDF files and in the museum database MuseumPro, which is based on FileMaker. Anyone who wants to know something about a farmstead, a street or a family today has to know the publications or sit down with someone from the museum at the computer or in the archive room.

The collection

So far, 24 publications have been processed into 2,543 text passages, including a volume on the art monuments of the entire district. In addition there are 1,786 inventoried photos and a register of 8,331 persons, buildings, addresses and field names. The archive holds further publications; they will be added to the system step by step. It is the collection of the Birmensdorf village museum of the Heimatkundliche Vereinigung.

Why a simple AI search is not enough

Keyword search

Finds names, does not understand meaning

Classic keyword search (BM25) hits farm names, family names and house numbers precisely. But it fails when the question uses different words than the text: asking about the “miller” does not find the passage about “grinding grain”. A typo leads nowhere.

Vector search

Understands meaning, blurs names

Semantic search over embeddings finds topics even when the wording differs. It handles exact names and numbers poorly: to it, house number 2 is close to 20, and one farm is close to the neighbouring farm. In the first draft, the language model also occasionally invented page numbers.

Combination

Only both together are enough

Hybrid search queries both methods at the same time and merges the results. Names and addresses additionally go through a register that catches typos. The same applies to photos: names and addresses are matched exactly in the picture description, topics such as “school” or “carnival” go through hybrid search.

Note: This page and the GitHub repository contain no texts, photos or data from the museum collection. The rights to them lie with the association.

A search from A to Z: the question about the mill

A single question shows how intent router, register, search and verification work together, and where the system deliberately stops.

  1. The question arrives. In the web chat or on Telegram, someone asks: “Who ran the mill?”

  2. The question is understood (intent router). A single call to the language model recognises the intent: knowledge question, photo search, question about the collection or greeting. It extracts subject and place from the question (entity extraction) and, if needed, rephrases it as a self-contained search query (query rewriting). The result comes back in a fixed schema and is validated (structured outputs).

  3. The place is set (metadata filter). During testing it became clear that the data model needs a place. So it was extended: every text passage now carries two metadata fields, the type of source and the municipality. If the question names no municipality, Birmensdorf applies. The filter admits all passages from the association's publications, but only the Birmensdorf sections from the district-wide volume.

  4. Search (hybrid search). Semantic search over embeddings (dense retrieval) and keyword search with BM25 (sparse retrieval) run in parallel. Reciprocal rank fusion merges both rankings into one. For names and addresses, an exact register search is added that catches typos through fuzzy matching.

  5. Verify (reranking and relevance threshold). A language model scores every retrieved passage on a scale from 0 to 3, following the LLM-as-a-judge principle. If no passage clears the threshold, a guardrail kicks in: the system reports that the collection holds no information and does not generate an answer at all. This prevents hallucination.

  6. Answer with evidence (grounding). The language model writes the answer only from the verified passages and inserts numbered markers. The source line with issue and page is built by the program code from a verified catalogue, so the model cannot invent a page number.

  7. The follow-up question (pronoun resolution). “Are there photos of it?” The “it” is resolved from the conversation history. The photo search itself works without a generative language model: it matches names exactly and searches topics in hybrid mode as with the texts, and it distinguishes what is shown in a picture from who took it. Where rules and search are sufficient, no language model is needed. That is best practice: it saves cost and response time and makes the result reproducible.

Combining general and specific sources. The volume on the art monuments of the Dietikon district is a general source. It makes up about 60 % of the text and also describes mills in neighbouring municipalities. The association's publications are specific; they deal only with Birmensdorf. Without a distinction, the large source would have crowded out the small ones and mixed up the mills. The solution is an attribute to filter on: during ingestion, every passage receives the municipality as metadata. Since then the answer stays with Birmensdorf, and the question about the mills in Dietikon still works. The pattern applies generally: anyone who combines sources of different scope in one index needs an attribute to control the selection.

Observability: Every request is logged with response time, number of hits and rating, without IP addresses and with a pseudonymous session ID. This shows which questions remain open and where the system is weak. Today the log sits in its own SQLite database. A self-hosted observability tool such as Langfuse is planned, which makes every step of a request traceable (tracing).

Why gpt-4o-mini

A RAG search does not need a frontier model. The knowledge comes from the retrieved passages; the model has to understand, assess and summarise them cleanly, but not contribute knowledge of its own. An early comparison confirmed this: the larger gpt-4o reached the same recall, but answered only 2 of 5 questions without evidence correctly, while gpt-4o-mini answered 4 of 5. With the later relevance threshold it is 5 of 5 today. On top of that, the smaller model costs about one fifteenth per token. In the spirit of FinOps, the choice therefore fell on gpt-4o-mini.

Own code without a framework

Many AI applications today are built with frameworks such as LangChain or LlamaIndex, or with the agent SDKs of the model providers, for example from Anthropic, Google or OpenAI. They bundle recurring building blocks and put an abstraction layer over the Python code. Here I deliberately did without: I wanted full transparency and to be able to see, measure and explain every step individually. With two search paths and one language model, a framework would have simplified little. The orchestration is therefore my own Python code with FastAPI and Pydantic.

The rules: governance in eight principles

These principles define how the system handles sources, people and data. They are implemented in the code and the infrastructure; the remaining points will be addressed before the opening to the public.

  1. Deterministic before language model

    What fixed rules handle reliably runs without a language model: name matching, photo search, source line, questions about the collection from the catalogue, and greetings. The model is used where language has to be understood or relevance has to be weighed. This keeps the system reproducible, cheap and fast.

  2. No statement without evidence in the collection

    Every answer is based on retrieved passages (grounding). If they do not reach the relevance threshold after reranking, the system stops before answering and reports that the collection holds no information. This threshold is the most important guardrail against hallucination.

  3. Code builds the citation

    The language model only inserts reference markers in the text. The visible source line with title, issue number and page is generated by the program code from the catalogue (deterministic citations).

  4. Respecting rights to the content

    Texts, photos and collection data belong to the association's collection. They are not in the public repository, nor are the test questions, because they contain content from the archive. The rights for public use are being clarified with the association.

  5. Personality rights and copyright: opening only after clearance

    The publications name many people, living and deceased, along with places of residence and properties, and the photo archive shows them. Most of it is likely to be unproblematic. But someone who appears in a printed booklet has not automatically agreed to a digital search: a booklet you pick up in the museum becomes a search that finds every name instantly. On top of that come the copyrights of the authors and photographers. The legal situation has been researched. Before going live, five rules therefore apply: a rights register per publication with written consent from the authors or their heirs; third-party reference works only with the publisher's permission; recognisable living persons in photos only with consent, otherwise withheld or anonymised (privacy by design); sensitive passages excluded from search; a simple way to object and request removal. Until then the chat stays closed. It will only be opened after this clearance and with the association's consent. A general overview for similar projects is available under Legal considerations on GitHub.

  6. Secured interfaces

    The system follows the principle of least privilege and keeps the attack surface small. The API and the vector database cannot be reached from outside; the containers are separated from each other in the Docker network (network segmentation). Only the web interface and the Telegram webhook can be reached from outside, both through a reverse proxy with TLS encryption. The webhook checks a secret token, and a rate limiter caps requests per session. Maintenance and data uploads run through an SSH tunnel.

  7. Measure before changing

    Every change to data preparation, search or prompts goes through the evaluation across all four test suites before it is adopted. The evals serve as regression tests: an improvement in one place must not make another worse.

  8. Observability and transparency

    The system should be traceable while storing as little personal data as possible. Logs show what the chat did for each request and make errors and gaps visible. Because questions themselves can contain names or addresses, data minimisation applies: no IP addresses, a pseudonymous session ID. Before the opening, a notice in the chat will be added stating that an AI is answering and what is logged, as the EU AI Act has required for chatbots since August 2026, together with a fixed retention period with automatic deletion. With the planned move to Langfuse, personal data will be masked before it is stored.

Insights

What I take away from the project. The list grows with the project.

  • Clean data beats a bigger model.In the data ingestion pipeline, more than 5,400 words split by hyphenation were repaired, sentences across page boundaries were joined and index pages were filtered out as false hits (data cleansing). This raised recall without changing anything about the model.
  • The ingestion pipeline runs fully automated.From reading the PDFs and the photo list to the finished index, everything runs in Python; not a single manual step in Excel is needed any more. Design and construction of the pipeline could largely be handed to a frontier model, and the result ran practically flawlessly. New material can be loaded with little effort.
  • A bigger model does not automatically deliver more.gpt-4o found no more than gpt-4o-mini, but more often invented answers where the collection held nothing. For RAG, what counts is what the search delivers, not the size of the model.
  • Names need a register.Vector search finds topics, but not an exact house number. Names and addresses therefore go through an exact search and a register that catches typos.
  • Every change is measured.Several ideas that sounded good did not hold up in measurement, such as the bigger model or searching over AI summaries of the texts. Without a test set there is no reliable statement about quality.
  • A natural conversation is design work.Conversation design is the most demanding part of conversational AI. A RAG chat needs fixed rules where reliability counts (source line, “no information”, greeting) and the flexibility of the language model where language has to be understood (follow-up questions, references back, free wording). An early version attached fifteen raw text blocks even to a “Hello”. Drawing the line between rule and model so that the conversation feels natural takes many rounds.

in operationplannedgovernance and protection
  1. User interfaces: web chat (Streamlit) and Telegram bot. In front of them sits Traefik as a reverse proxy: it receives all requests from outside, routes them to the right service and encrypts the connection (TLS with certificates from Let's Encrypt).
  2. Protection layer: the API and the database cannot be reached from outside. A rate limiter counts requests per hour in a sliding time window and throttles above 60. The Telegram access checks a secret token with every message, so that only Telegram itself can call the server.
  3. Planning and register: the planner is the system's intent router. A single model call recognises intent, subject and place and resolves references such as “it” or “she” from the conversation history (pronoun resolution). The name register with 8,331 entries is held in memory and matches names approximately (fuzzy matching), so that a doubled letter or a missing “h” still leads to the right farmstead.
  4. Search and verification: hybrid search finds candidates by meaning and keywords. A language model scores each candidate (reranking). Then the relevance threshold, in technical jargon the “gate”, decides whether an answer is produced at all: if no passage reaches the threshold, the system honestly says “no information”.
  5. Answer and citations: the model formulates the answer only from the verified passages and inserts markers. The code replaces the markers with the source line including issue and page, and points to matching photos if there are any.
  6. Storage and models: Qdrant stores all text passages and photo records with their vectors and metadata. A manually verified catalogue of the publications supplies title, issue and year for the source line. The photos are served by a dedicated image server.
